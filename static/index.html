CPU vs GPU: similarity search

Time to score one question against N document vectors (768 dims) and pick the top results. Median of 20 runs. Every GPU kernel is checked against NumPy for identical top-10 results before it's timed.

What the numbers teach

  1. Small inputs: the CPU wins. Launching GPU work has a fixed cost (~0.2 ms). With only a few hundred chunks, that overhead is bigger than the work itself.
  2. Large inputs: the GPU wins. Once there's enough work to fill thousands of GPU threads, the fixed cost disappears into the total.
  3. This search is memory-bound. Each number is used once (1 multiply + 1 add per 4 bytes read), so speed is limited by how fast memory can be read, not by maths. Our v2 kernel already reads at ~80 GB/s, close to the M2's ~100 GB/s peak.
  4. So the best optimisation was to read fewer bytes. Kernel v3 stores vectors as 16-bit floats, halving the data read. It ends up about 2× faster than v2, and faster than Apple's general-purpose library, with the same top-10 results.
  5. Batching makes it compute-bound. 64 questions at once reuse each document vector 64 times, so the GPU's maths units finally get busy (see the batched result).

2 · Why a GPU?

CPU · 8 cores

A few powerful cores, built to finish one task quickly. Good at branching, sequential logic.

GPU · 1,024 ALUs (M2, 8 cores × 128)

Many simple lanes that run the same instruction on different data (SIMD). Good for work that splits into thousands of independent pieces.

Scoring a chunk = dot(chunk, question) = 768 multiply-adds. The scores don't depend on each other, so every chunk can be scored at the same time. This kind of problem is called “embarrassingly parallel”.

3 · Similarity = dot product

Text with similar meaning gets vectors pointing in a similar direction. With all vectors scaled to length 1:

score(chunk, q) = Σd=1..768 chunk[d] × q[d] = cos θ

1.0 = same meaning · 0 = unrelated. For N chunks that's N × 768 multiply-adds per question, e.g. 115 million for 150k chunks.

4 · Three kernels, each faster than the last

v1 · Naive

1 thread = 1 chunk. Each thread loops over all 768 numbers by itself.

Neighbouring threads read addresses 3 KB apart, so the reads can't be merged (uncoalesced).

v2 · SIMD-group + float4

32 threads (one SIMD-group, like a CUDA “warp”) share 1 chunk. Lane i reads float4 #i, then #i+32…

Neighbouring lanes read neighbouring memory (coalesced), 16 bytes per load. simd_sum() adds the 32 partial results in hardware.

v3 · + half precision

Same as v2, but vectors are stored as 16-bit halfs. Maths is still done in 32-bit.

The kernel was memory-bound, so halving the bytes read nearly halved the time. Top-10 results are unchanged.

Show kernel v2 source (Metal Shading Language) 
uint N    = docs_shape[0];
uint lane = thread_index_in_simdgroup;               // 0..31
uint row  = threadgroup_position_in_grid.x * ROWS_PER_TG
          + simdgroup_index_in_threadgroup;          // which chunk
if (row >= N) return;

const device float4* doc4 = (const device float4*)(docs + row * D);
const device float4* q4   = (const device float4*)(query);

float acc = 0.0f;
for (uint i = lane; i < D / 4; i += 32)            // 192 float4s → 6 per lane
    acc += dot(doc4[i], q4[i]);                      // 4 multiply-adds at once
acc = simd_sum(acc);                                 // add 32 lanes in hardware
if (lane == 0) scores[row] = acc;

6 · How is this different from ChatGPT?

  • Private. Papers never leave the laptop, so it's safe for unpublished, medical or legal documents.
  • Offline & free. No internet, account or API bill.
  • Verifiable. Every claim cites paper + page. Click a citation to open that exact page.
  • Admits gaps. If the answer isn't in your papers, it says so instead of guessing.
  • Scales. Searches every chunk of every paper in milliseconds on the GPU.
  • Trade-off: a 3B local model writes less fluently than GPT-4-class models.
